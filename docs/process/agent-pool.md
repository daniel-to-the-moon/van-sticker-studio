## 2. 评审路由

合并所需的独立评审必须来自未参与实现、非本体系的评审者（AGENTS §0、§8、§13）。资源池指派 `review` 任务时按下表执行。

| 实现方 | 合格评审者（建议优先顺序） | 不合格 |
| --- | --- | --- |
| GPT 体系（Codex、GPT 云任务） | Claude、Grok、Muse | dot、GPT CI 评审、Codex |
| Claude | Codex、GPT CI 评审、dot、Grok、Muse | Claude |
| Muse 体系（Muse、Pubby） | dot、Claude、Grok | Muse、Pubby |
| Grok 体系（Grok、Clara） | Codex、dot、Claude、Muse | Grok、Clara |
| 维护者本人参与实现 | 任一未参与该实现的 agent | 参与过该实现的执行者 |

- 现状的缺口：Codex 实现的 PR 不能由 dot 或 GPT CI 评审放行，二者都属于 GPT 体系。
- 一个 PR 有多个实现方时，所有实现方的体系都不合格。
- 路由表只决定谁可以评，不决定评审结论是否被接受；接受仍归 dot。

## 3. 辅助资源池

### 3.1 任务类型

| 类型 | 内容 | 默认受派者 |
| --- | --- | --- |
| `search` | 检索事实、资料、标准、接口文档 | 能联网的任一执行者 |
| `research` | 市场调研、竞品、需求整理报告 | 调研员 |
| `review` | 协助评审某个 PR 的当前 head | 按 §2 路由 |
| `evidence` | 补证据：复现、截图、只读检查 | 能运行代码的执行者 |
| `tooling` | 工具调研：查找、比对、在自己的隔离环境里试用，给出建议 | 能运行代码的执行者 |

**不进资源池：** 实现任务、合并、上线、回滚、标签和治理改动、保留项、任何需要密钥或账号授权的操作。

### 3.2 队列

- 每个辅助任务是一个 Issue，或者原 Issue/PR 下的一条请求评论。
- 标签候选为 `pool:search`、`pool:research`、`pool:review`、`pool:evidence`、`pool:tooling`。建标签属于仓库设置，由维护者决定；建好之前，用标题前缀 `[pool:<类型>]`。
- 状态记在评论里，不另建状态标签。

### 3.3 生命周期

1. **请求**：任何角色都可发起。写明类型、问题、交付物、截止时间；评审类还要写 PR 编号、head SHA、不合格的体系。
2. **登记**：调度员核对格式，补标签或前缀。
3. **指派**：调度员评论 `指派：<执行者>`，依据 §3.4 的能力登记和 §2 的路由表。
4. **回执**：受派者评论接受，这条评论等同 claim。超时没有回执的，调度员改派。
5. **交付**：受派者在原处交付，首行署名“执行者：<名字>”。
6. **关闭**：请求方写明采用或不采用，然后关闭。

超时默认值（回执、交付）由 dot 定：[NEEDS CLARIFICATION]。

### 3.5 调度员的约束

- 不派实现任务；派单权仍归 dot。调度员和 dot 的安排冲突时，以 dot 为准。
- 不把 Grok 体系 PR 的评审指派给 Grok 体系。
- 调度员自己接辅助任务时，交付由 dot 或另一个执行者核对。
- 指派不产生权限，也不认证身份（constitution §11）。

## 4. 工具与下载边界

- 只在执行者自己的隔离环境里下载和试用。不进仓库，不写进 `package.json` 或锁文件，不新增依赖（AGENTS §1），除非任务明确要求。
- `tooling` 的交付物是建议：工具名、版本、来源、许可证、风险、试用结果。要不要采用，由 dot 决定是否开实现任务。
- 不使用、不索要、不转交任何密钥；不安装需要账号授权的工具。
- 不执行来源不明的脚本；不把仓库私有文件上传到第三方服务。

## 5. 唤醒与轮询

- 每个执行者至少登记一种可靠的唤醒方式（§3.4）：GitHub 事件、自己的定时运行，或维护者转达。
- 调度员扫描队列的频率：[NEEDS CLARIFICATION]，建议不低于每天一次。
- 只能靠维护者转达的执行者，不承担截止时间短于一天的任务。
